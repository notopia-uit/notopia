# Terraform Code Review — Notopia Infrastructure

> Generated by terraform-engineer skill audit. Review date: 2026-07-06

## 1. Critical Issues

### C1. Grafana IAM Role Uses `AdministratorAccess`

**File:** `modules/monitoring/main.tf:40-43`

```hcl
resource "aws_iam_role_policy_attachment" "grafana_admin" {
  role       = aws_iam_role.grafana.name
  policy_arn = "arn:aws:iam::aws:policy/AdministratorAccess"
}
```

This grants the Grafana workspace **full admin access** to the entire AWS account. This is a catastrophic over-permission. Grafana only needs `cloudwatch:*`, `aps:*` (Prometheus), and `logs:*` read access. An attacker who compromises the Grafana workspace can do anything in the account — delete the RDS cluster, modify IAM, exfiltrate data.

**Fix:** Replace with a custom inline policy scoped to the specific Prometheus workspace and CloudWatch namespaces needed.

### C2. Hardcoded Secrets in ECS Container Environment Variables

**File:** `modules/ecs/main.tf`

Multiple services embed plaintext secrets directly in `container_definitions` as environment variables, despite the variables being marked `sensitive` at the variable level:

- `AUTHENTIK_CLIENT_ID` and `AUTHENTIK_SECRET` in web task
- `NOTOPIA_NOTE_DATABASE_URL` contains `db_password` in cleartext
- `NOTOPIA_NOTE_AUTHENTIK_TOKEN`
- `NOTOPIA_DOCUMENT_DB_PASSWORD`
- `NOTOPIA_AUTHORIZATION_DATABASE_URL` contains `db_password`
- `AUTHENTIK_POSTGRESQL__PASSWORD` and `AUTHENTIK_SECRET_KEY` in authentik tasks

The `sensitive = true` flag on variables only prevents Terraform CLI output from displaying the values — it does **not** prevent secrets from being stored in plaintext in the ECS task definition (visible in the AWS console, CloudWatch, and CloudTrail). Anyone with ECS read permissions can see these credentials.

**Fix:** Move all secrets to AWS Secrets Manager or SSM SecureString parameters and reference them via the ECS `secrets` block (like `meilisearch_api_key` is already done correctly). The note service already does this correctly for the Meilisearch key — extend that pattern to all secrets.

### C3. MSK `kms_key_arn` Defaults to Empty String — Encryption at Rest May Be Silently Disabled

**File:** `modules/msk/variables.tf:33-34`, `modules/msk/main.tf:23`

```hcl
variable "kms_key_arn" {
  type    = string
  default = ""
}
```

The `encryption_at_rest_kms_key_arn = var.kms_key_arn` is set to `""` by default. When an empty string is passed to the MSK provider for this argument, behavior depends on provider version — it may fall back to AWS-managed keys, but it's unclear and fragile. The environments never pass `kms_key_arn`, so this defaults to empty.

**Fix:** Either create a KMS key and pass it explicitly, or remove the `encryption_at_rest_kms_key_arn` attribute entirely (MSK uses AWS-managed keys by default when the attribute is omitted). Document which encryption is actually in play.

## 2. Warnings

Not a single variable has a `validation` block. Critical candidates:

- `environments/dev/variables.tf`: `domain_name` — no regex check, empty string accepted

### W3. `count` Used Where `for_each` Would Be More Robust

**File:** `modules/networking/main.tf`

All subnet, EIP, NAT, and route table resources use `count` with `length(...)`. This means inserting or removing an element in the middle causes Terraform to destroy and recreate resources after the change point.

**Fix:** Use `for_each` with a map keyed by AZ name to get stable resource addresses:

```hcl
for_each = { for i, cidr in var.public_subnet_cidrs : var.availability_zones[i] => cidr }
```

---

### W4. Dev and Prod Environments Are Near-Identical Duplicated Code

**Files:** `environments/dev/main.tf`, `environments/prod/main.tf`

The two environment files are nearly identical (~151 lines each) with only a few value differences (instance classes, counts, `single_nat_gateway`, `log_retention_days`). This is textbook duplication.

**Fix:** Extract shared configuration into a common module or use a Terragrunt-style configuration. At minimum, use a `locals` block with environment-specific values and a single `main.tf` that reads from a variable map.

## 3. Suggestions

### S1. Add `prevent_destroy` Lifecycle to Production RDS and ElastiCache

**Files:** `modules/rds/main.tf`, `modules/elasticache/main.tf`

For prod, these stateful resources should have:

```hcl
lifecycle {
  prevent_destroy = true
}
```

This prevents accidental `terraform destroy` from wiping a production database.

---

### S2. S3 Bucket: Add Transition Rules for Cost Savings

**File:** `modules/s3/main.tf`

The document bucket has no IA/Glacier transition rules. For documents older than 90 days, transitioning to S3 Standard-IA saves ~40%. Add:

```hcl
rule {
  id     = "transition-to-ia"
  status = "Enabled"
  transition {
    days          = 90
    storage_class = "STANDARD_IA"
  }
}
```

---

### S3. Add `default_tags` to AWS Provider

**Files:** `environments/dev/versions.tf`, `environments/prod/versions.tf`

Neither environment configures `default_tags` on the AWS provider. This means every resource must manually include tags. Adding:

```hcl
provider "aws" {
  region = var.aws_region
  default_tags {
    tags = {
      Project     = "notopia"
      Environment = var.environment
      ManagedBy   = "terraform"
    }
  }
}
```

This ensures all resources are consistently tagged without manual tag blocks.

---

### S4. Consider Using AWS Secrets Manager Instead of SSM for Database Credentials

**Files:** `environments/dev/main.tf`, `environments/prod/main.tf`

The Meilisearch key correctly uses SSM SecureString, but database passwords and Authentik secrets are passed as Terraform variables and embedded directly. AWS Secrets Manager provides automatic rotation, versioning, and audit trails — better suited for long-lived credentials like DB passwords.

---

### S5. Unused Availability Zones Data Source

**Files:** `environments/dev/data.tf`, `environments/prod/data.tf`

Both environments define `data "aws_availability_zones" "available"` but never use it. The `availability_zones` variable is hard-coded as a default. Either use the data source dynamically or remove the unused data block.

---

### S6. ECS Services Missing `deployment_circuit_breaker`

**File:** `modules/ecs/main.tf` (all ECS service resources)

None of the ECS services configure `deployment_circuit_breaker`. This means a bad deployment can keep rolling out. Add:

```hcl
deployment_circuit_breaker {
  enable   = true
  rollback = true
}
```

---

### S7. ECS Services Missing `enable_execute_command`

**File:** `modules/ecs/main.tf`

For debugging in dev, `enable_execute_command = true` allows `aws ecs execute-command` into containers. Not needed for prod, but valuable in dev.

---

### S8. ALB Access Logging Not Enabled

**File:** `modules/alb/main.tf`

The ALB has no access logging configured. For security auditing and debugging, ALB access logs should be enabled and stored in an S3 bucket. This is a PCI-DSS requirement if handling payment data and best practice regardless.

---

### S9. RDS Cluster Missing `deletion_protection`

**File:** `modules/rds/main.tf:31-49`

The RDS cluster has no `deletion_protection` attribute. For prod, this should be `true`.

---

### S10. SSM Parameter Missing `description`

**File:** `environments/dev/main.tf:85`, `environments/prod/main.tf:85`

The `aws_ssm_parameter` for Meilisearch key lacks a `description` attribute.
