2026-11-24 Detail ​

Period: 2026-10-25–2026-11-24 Repository baseline: 69929a45c1878d22830b3417279c631ab69a883c (exclusive; dated 2026-10-24) End commit on main: db8c80a424b8833dc169a838e846b0c002d59ffe (inclusive)

This period focused on billing reliability, Kubernetes deployment preparation, and API and tooling improvements. Local billing UAT covered several payment flows but left high-risk cases open; homelab deployment has not yet been verified end to end.

Repository evidence is limited to what landed on main in the commit range; pending PRs are referenced only as future work. A few commits in the range are dated 24 October. The billing UAT workbook and progress log are supplemental evidence published separately, and the homelab status includes information supplied by the project owner. The AI backend work merged in 6edb58723852 is excluded because it was reported earlier.

1. Billing reliability and contracts ​

Domain and transaction improvements ​

  • Refactored billing domain models and value objects, including money, payment, price, subscription, and refund-related types. The changes clarify ownership and invariants and reduce accidental mutation. Further cleanup removed unused contact-update behavior. See #365, d78e47a3, and 709bd76e.
  • Introduced a transactional outbox: billing database writes and outgoing events are persisted in the same transaction, then forwarded asynchronously. Provider cancellation and refund submission are driven by outbox events. This reduces the risk of a committed state change without a corresponding event; it does not remove the need for retries and idempotency. See d78e47a3 and the billing documentation.
  • Improved duplicate checkout handling under a workspace account lock and refund settlement handling, including not reopening settled refunds. Added or updated tests around billing domain behavior, provider interactions, and webhooks (d78e47a3).
  • Made billing features and limits explicit types across the contract and dependent services, rather than relying solely on generic string keys (f758ec9c, 18cca64c).
  • Fixed Stripe customer-portal catalog configuration by specifying allowed update fields (5196957d), and improved sandbox customer descriptions (775223ce).

API improvements ​

  • Changed GET /billing/workspaces/{workspaceId}/subscription to GET /billing/workspaces/{workspaceId} because the response contains both subscription and payer, either of which may be null. Updated nullable response fields and required-field declarations (a780d8bb). This is a route change for API consumers.
  • Expanded examples for plans, free workspace entitlements, and billing responses and clarified operation descriptions and webhook tagging (ec85c290, a60d17ec, 9e01d768, f6d2060c, 2add6fca).

Manual Stripe sandbox UAT ​

Manual testing was performed through Scalar and a Stripe sandbox. The billing UAT workbook and progress log are published separately on GitHub Gist, not committed as report attachments. A complete billing UI was not available for this test; results do not establish an end-user UI flow or production readiness.

2. Kubernetes, Helm, and homelab ​

Implemented ​

  • Added a shared Helm library and service charts for web, note, authorization, billing, document, and search-worker, plus an authenticated edge. A chart for the existing AI service was included in later deployment work. Charts include service-specific values, schemas, workload/service resources, optional autoscaling and disruption controls, migration or seed hooks where applicable, and automated chart checks. See #370 (72beeadf) and #379 (8c90e9bb).
  • Prepared applications for deployment: separated migration and mandatory-data initialization commands, added or improved health/readiness behavior, and adjusted deployment-related configuration. Search-worker readiness accounts for Kafka connectivity; document includes dependency readiness and a migration runner.
  • Prepared Flux-based homelab GitOps wiring for releases and infrastructure, including databases, Meilisearch, Valkey instances, and encrypted secret manifests (#376, 3af652e4). Upgraded the Valkey Helm chart to 1.0.0 (46201ed2); this refers to the chart version, not a claim that the Valkey server is version 1.0.0.
  • Added Kubernetes CI and service-release automation, chart version checks, release tag scripts, and an initial development release (8c90e9bb, a97d424b). Improved test reporting and reduced duplicate CI runs (c97d3dad, d1aaf760, 7766cc6d).
  • Prepared additional homelab values and secrets, plus RustFS and Stripe webhook setup documentation (6e9f301f, 4522f0b6). Not all inputs are filled.

Still in progress / deployment gates ​

The project owner reports that homelab secrets and environment values are being populated and RustFS is being configured. The application has not yet been deployed and verified end to end on the homelab.

Before treating the deployment as ready, the documented Kubernetes limitations call for live verification of identity-header boundaries and direct-access prevention, authorization policy seeding and safe recovery, image permissions and filesystems, health and routing, and upgrades. Document replica event delivery also has known limitations. Rendered charts and unit tests are useful but cannot prove these live-cluster properties.

3. API correctness and developer authentication ​

  • In 234f7efa, introduced separate creation request schemas for folders, notes, and workspaces instead of reusing full resource/response schemas. The latter include server-generated, read-only fields that may be required in responses but should not be required from clients. The note API was already OpenAPI 3.1.2 before this commit; this was a contract correction for 3.1 validation, not an upgrade from 3.0 to 3.1 in this reporting range.
  • OpenAPI 3.1 treats readOnly as a JSON Schema annotation and discusses applying required in the relevant request/response context; tooling can interpret this differently. Separate schemas make the input contract explicit and avoid relying on validator-specific behavior. Reference: OpenAPI 3.1.2 Schema Object: readOnly and writeOnly.
  • Enabled local Authentik fixture users and the API viewer client for password-grant testing (a115e9d0), complementing authorization-code and refresh-token configuration (aba81097). These fixture credentials and password grants are for local development; do not generalize them to production use.
  • Expanded OAuth default scopes for API exploration (17cc93ac). Updated Redocly CLI to 2.82.0 (2e80d890); the update did not require application code changes.

4. Toolchains, dependencies, and build quality ​

  • Split mise into shared, dev, and CI environments and added per-environment lockfiles (711a6384, 201943ad). The split avoids installing local-only tools in CI and vice versa; locked versions, checksums, and dependency graphs support repeatable installations across machines. See mise tooling.
  • Upgraded the gRPC/Protobuf toolchain (#391, 93c0910c): Buf 1.65.0 → 1.75.0, ts-proto 2.12.4 → 2.22.0, Go gRPC 1.84.0 → 1.85.0, @bufbuild/protobuf 2.11.0 → 2.17.0, protobufjs 8.4 → 8.8, and related validation dependencies. Regenerated TypeScript protobuf output and made proto lint cache sensitive to Buf upgrades. Later updated Go protovalidate to 1.4.1 (a349cfe8).
  • Removed apps/document/inquire-shim.js, not a generated proto stub (#392, eabfdb45). It had worked around protobufjs dynamic module loading in Rspack; the replacement no longer matched a dependency, and the service uses generated ts-proto package definitions instead of loading .proto files at runtime. The recorded investigation found byte-identical application bundles with and without the shim. See the bundling investigation and gRPC proto-loader investigation.
  • Other notable updates include Node 26, Go 1.27.4, Nx 24.0.6, NestJS 11.2.11, TypeORM 1.1.3, Next.js 16.4.6, Vitest 5.1.1, Rspack 2.3.3, oapi-codegen 2.9.0, and OpenAPI Generator CLI 2.42.2. Infrastructure updates included PostgreSQL 18.7, Meilisearch 1.57, Grafana 13.3.1, Tempo 3, and updated Authentik, Redpanda, and RustFS images. These are selected examples, not an exhaustive dependency inventory.
  • Aligned Go and Node OpenTelemetry dependencies (#380); pinned cron to 4.4.0 for compatibility with @nestjs/schedule (0a59ca58). Enabled type-aware Oxlint and fixed identified issues (891cecbe, 00cd90e2).

6. Future work and dependencies ​

Near term ​

  1. Finish RustFS and other homelab inputs, deploy the prepared releases, and run live security, startup, upgrade, and application-flow checks.
  2. Resume prioritized billing UAT and add suitable automated integration coverage for duplicate charges, authorization, and webhook recovery. Resolve the logging and token/session security follow-up.
  3. NestJS 12: wait for a compatible stable Nx release and confirm its Nest peer ranges before upgrading. The 2026-11-21 plan records upstream Nx support merged, but not yet available in the stable release used at that snapshot. #350 covers the Nest upgrade; #396 is a Terminus maintenance update, not the core blocker. The plan identified a search-worker Kafka mock requiring adaptation because Nest 12 makes createClient asynchronous; this was a migration finding, not a completed fix.
  4. Native ESM: evaluate separately for document, AI, and search-worker. OpenTelemetry does not categorically prohibit ESM, but instrumentation must start before application imports and may require an ESM loader hook; Nest-specific instrumentation also has its own version-support limit. Align build output, telemetry preload, Docker and Kubernetes commands, migration/seed entrypoints, and verify actual logs, traces, startup, and shutdown. BlockNote compatibility is related but does not inherently block ESM or require an ESM application bundle. This is a plan, not an implemented migration. Source: docs/superpowers/plans/2026-11-21-nestjs-12-native-esm-migration.md (7374de9f).
  5. TypeORM extension: consider #346, including CLI and fixture validation. The plan records that extension 3.9.0 has an older TypeORM peer range while the project already resolves TypeORM 1.1.3.

Longer term ​

  • Evaluate BlockNote 0.55 → 0.57 (#238), including its ESM-only distribution, server-side DOM API changes, and Yjs compatibility. Investigate whether its version-history facilities can satisfy some of the current manually saved Yjs revision and rollback requirements; compatibility and the version in which the feature first appeared have not been verified. Examples for future review: Yjs 14 versioning and versioning extension. Do not assume that adopting the feature or Yjs 14 is appropriate without further investigation.
