The SSE Ghost That Lived After the Request Died ​

A story about a goroutine that didn't know when to quit, a pipe that got closed under its feet, and the panic that followed.

Written, fixed by AI, in commit a9be674771dc -> e023ee0c6609

The Setup ​

Notopia's note service has a real-time feature: when you open a workspace in the browser, the frontend opens a persistent HTTP connection to /note/workspaces/:workspaceId/events and listens for changes — a note was renamed, a folder was moved, someone joined. This is implemented with Server-Sent Events (SSE), a simple standard where the server streams newline-delimited text over a single long-lived HTTP connection.

On the Go side, the API is generated by oapi-codegen from an OpenAPI spec. The spec declares the endpoint with text/event-stream response type, and the tool generates a server interface, request/response types, and a strict handler dispatcher. The actual streaming logic — what to send, when, and how to keep the connection alive — is left for us to implement.

The first implementation worked, until it didn't.

The Crime Scene ​

The symptoms appeared in the logs like this:

time=2026-05-23T07:03:04.031Z level=WARN msg="failed to send heartbeat" error="failed to write heartbeat SSE event: io: read/write on closed pipe"
time=2026-05-23T07:03:04.031Z level=DEBUG msg="sent heartbeat"

Two lines. Same millisecond. One says it failed. The other says it succeeded. That is already suspicious — a log that contradicts itself is usually a goroutine that didn't know it was the ghost at its own funeral.

Then, when the client disconnected and reconnected, the server crashed hard:

[GIN-debug] [WARNING] Headers were already written. Wanted to override status code 200 with 500

panic: runtime error: invalid memory address or nil pointer dereference
[signal SIGSEGV: segmentation violation code=0x1 addr=0x0 pc=0x57c592]

goroutine 1701 [running]:
bufio.(*Writer).Flush(0x1?)
    net/http/server.go:405 +0x39
net/http.(*response).FlushError(...)
net/http.(*response).Flush(...)
github.com/gin-gonic/gin.(*responseWriter).Flush(...)
github.com/notopia-uit/notopia/internal/note/controller/http.(*workspaceEventSSESender).sendHeartBeat(...)
    internal/note/controller/http/sse.go:86 +0x2a3

bufio.(*Writer).Flush(0x1?) — that 0x1? in the argument is Go's way of saying the pointer was effectively nil. The server process exited.

The Architecture of the Old Code ​

To understand what went wrong, we need to understand how the old code was structured.

What oapi-codegen generates ​

For an SSE endpoint, oapi-codegen generates two things relevant to us.

First, a response type for the 200 case:

go
type GetWorkspaceEvents200TexteventStreamResponse struct {
    Body          io.Reader
    ContentLength int64
}

func (response GetWorkspaceEvents200TexteventStreamResponse) VisitGetWorkspaceEventsResponse(w http.ResponseWriter) error {
    w.Header().Set("Content-Type", "text/event-stream")
    w.WriteHeader(200)

    flusher, ok := w.(http.Flusher)
    if !ok {
        _, err := io.Copy(w, response.Body)
        return err
    }
    buf := make([]byte, 4096)
    for {
        n, err := response.Body.Read(buf)
        if n > 0 {
            w.Write(buf[:n])
            flusher.Flush()
        }
        if err != nil {
            if err == io.EOF {
                return nil
            }
            return err
        }
    }
}

The idea here is: you give it an io.Reader, it reads chunks from it and writes them to the HTTP response, flushing after each chunk so the client sees data immediately. Simple and elegant for a static body. For a live stream it begs a question: who is writing to the other end of the pipe?

Second, the strict handler dispatcher:

go
func (sh *strictHandler) GetWorkspaceEvents(ctx *gin.Context, workspaceId WorkspaceIdPath) {
    // ... build request object ...
    response, err := handler(ctx, request)

    if err != nil {
        sh.options.HandlerErrorFunc(ctx, err)
    } else if validResponse, ok := response.(GetWorkspaceEventsResponseObject); ok {
        if err := validResponse.VisitGetWorkspaceEventsResponse(ctx.Writer); err != nil {
            sh.options.ResponseErrorHandlerFunc(ctx, err)
        }
    }
}

The dispatcher calls your application handler, gets back a response object, then calls VisitGetWorkspaceEventsResponse(ctx.Writer) on it. Everything is synchronous from the dispatcher's perspective — Visit runs in gin's handler goroutine and the dispatcher waits for it to return.

What the old application code did ​

The old GetWorkspaceEvents handler tried to bridge the gap by combining the generated io.Reader-based response type with a goroutine that does the actual event pumping:

go
func (h *StrictHandler) GetWorkspaceEvents(ctx context.Context, ...) {
    c := ctx.(*gin.Context)   // cast to get the ResponseWriter

    eventCh, _ := h.WorkspaceEventHub.Subscribe(ctx, ...)

    r, w := io.Pipe()
    sender := newWorkspaceEventSSESender(ctx, eventCh, w, c.Writer)
    sender.Stream()   // starts a goroutine

    return note.GetWorkspaceEvents200TexteventStreamResponse{Body: r}, nil
}

And the Stream goroutine:

go
func (s *workspaceEventSSESender) Stream() {
    ticker := time.NewTicker(30 * time.Second)
    go func() {
        defer ticker.Stop()
        for {
            select {
            case <-s.ctx.Done():
                s.writer.Close()
                return
            case <-ticker.C:
                if err := s.sendHeartBeat(); err != nil {
                    slog.Warn("failed to send heartbeat", ...)
                }
                slog.Debug("sent heartbeat")  // unconditional — runs even on failure
            case evt, ok := <-s.eventCh:
                _ = s.send(evt)  // error discarded
            }
        }
    }()
}

Where sendHeartBeat wrote to the io.PipeWriter and then called s.flusher.Flush() — and s.flusher was c.Writer, the gin ResponseWriter.

So at runtime, two goroutines were alive simultaneously:

GoroutineWhat it does
A — gin's handler goroutineRuns VisitGetWorkspaceEventsResponse: reads from PipeReader, writes to ResponseWriter, calls Flush()
B — the Stream goroutineOn each tick or event: writes to PipeWriter, calls Flush() on the same ResponseWriter

The Bugs ​

Bug 1: The mutex that protected nothing important ​

workspaceEventSSESender had a sync.Mutex. It was locked inside send() and sendHeartBeat() around the writes to the PipeWriter and the Flush() calls. This serialized concurrent calls within goroutine B.

But goroutine A — the generated Visit loop — never touched that mutex. It was calling w.Write() and flusher.Flush() on the same ResponseWriter completely independently. The mutex was protecting the wrong thing. The actual shared resource, the gin.ResponseWriter, had zero synchronization between the two goroutines.

This is a data race. The Go race detector would have flagged it. On most runs it was fine because the timing worked out — goroutine A was blocked on PipeReader.Read() while goroutine B was calling Flush(). But "fine most of the time" is exactly how latent concurrency bugs hide.

Bug 2: The unconditional "sent heartbeat" log ​

go
if err := s.sendHeartBeat(); err != nil {
    slog.Warn("failed to send heartbeat", ...)
}
slog.Debug("sent heartbeat")  // always runs

slog.Debug("sent heartbeat") is outside the error check. It runs whether or not sendHeartBeat failed. That is where the contradictory log lines came from — "failed to send heartbeat" followed immediately by "sent heartbeat" at the same millisecond. Not two separate heartbeats. One heartbeat that failed, and then a lie.

Bug 3: The discarded error ​

go
_ = s.send(evt)

The error from sending an actual workspace event was silently discarded. If a write failed, the goroutine just moved on, the event was lost, and nobody knew.

Bug 4: The crash — use-after-free on the ResponseWriter ​

This is the fatal one. Here is the sequence:

  1. Client connects. SSE stream runs normally.
  2. Client disconnects. Gin cancels the request context — ctx.Done() is now ready.
  3. In the select loop of goroutine B, both ctx.Done() and ticker.C might be ready at the same moment. Go's select picks among ready channels uniformly at random.
  4. If ticker.C wins, goroutine B proceeds to call sendHeartBeat().
  5. sendHeartBeat() writes to the PipeWriter. But by now, goroutine A (the Visit loop) may have returned — the PipeReader was closed by defer closer.Close(). Writing to a pipe with no reader gives io: read/write on closed pipe. The error check catches this and returns early, before calling Flush(). This is the "failed to send heartbeat" log.
  6. But. If the pipe write succeeded (maybe the pipe buffer still had space), execution falls through to s.flusher.Flush().
  7. Goroutine A has already returned from VisitGetWorkspaceEventsResponse. Gin has logged the completed request (status 200). The http.response object is being torn down. The internal *bufio.Writer inside it is set to nil during cleanup.
  8. s.flusher.Flush() → gin.responseWriter.Flush() → http.response.Flush() → bufio.Writer.Flush(nil) → nil pointer dereference → panic → process exit.

The goroutine outlived the request it was serving. It held a pointer to a ResponseWriter that no longer belonged to it. When it reached out and touched it, the process died.

The Fix: Stop Fighting the Framework ​

The root cause is the two-goroutine design. The generated Visit method runs in gin's goroutine and owns the ResponseWriter. The Stream goroutine runs separately and also touches the ResponseWriter. That tension is the source of every bug listed above.

The fix is to stop fighting the framework and work with the codegen pattern.

What the codegen actually offers ​

The generated strict handler dispatches like this:

go
} else if validResponse, ok := response.(GetWorkspaceEventsResponseObject); ok {
    if err := validResponse.VisitGetWorkspaceEventsResponse(ctx.Writer); err != nil {
        sh.options.ResponseErrorHandlerFunc(ctx, err)
    }
}

It calls VisitGetWorkspaceEventsResponse synchronously. It waits for it to return. This is the hook. If Visit blocks, gin's goroutine blocks — and that goroutine is the rightful owner of the ResponseWriter for the duration of the request.

The generated GetWorkspaceEvents200TexteventStreamResponse is just one concrete type that satisfies the GetWorkspaceEventsResponseObject interface. We are not required to use it. We can implement our own type.

The new implementation ​

go
type WorkspaceEventStreamResponse struct {
    ctx     context.Context
    eventCh <-chan app.WorkspaceEvent
}

var _ note.GetWorkspaceEventsResponseObject = (*WorkspaceEventStreamResponse)(nil)

func (r *WorkspaceEventStreamResponse) VisitGetWorkspaceEventsResponse(w http.ResponseWriter) error {
    w.Header().Set("Content-Type", "text/event-stream")
    w.Header().Set("Cache-Control", "no-cache")
    w.Header().Set("Connection", "keep-alive")
    w.WriteHeader(http.StatusOK)

    flusher, ok := w.(http.Flusher)
    if !ok {
        return fmt.Errorf("response writer does not support flushing")
    }
    flusher.Flush()

    ticker := time.NewTicker(30 * time.Second)
    defer ticker.Stop()

    for {
        select {
        case <-r.ctx.Done():
            return nil
        case <-ticker.C:
            if err := writeHeartBeat(w); err != nil {
                slog.Warn("failed to send heartbeat", slog.Any("error", err))
                return nil
            }
        case evt, ok := <-r.eventCh:
            if !ok {
                return nil
            }
            if err := writeWorkspaceEvent(w, evt); err != nil {
                slog.Error("failed to send event", slog.Any("error", err))
                return nil
            }
        }
        flusher.Flush()
    }
}

And the handler becomes:

go
func (h *StrictHandler) GetWorkspaceEvents(ctx context.Context, ...) (note.GetWorkspaceEventsResponseObject, error) {
    user, ok := commonhttp.UserFromContext(ctx)
    if !ok {
        return nil, errs.Unauthorized
    }

    eventCh, err := h.WorkspaceEventHub.Subscribe(ctx, request.WorkspaceId, user.ID)
    if err != nil {
        return nil, errs.NewInternalErr("failed to subscribe to workspace events", err)
    }

    return NewWorkspaceEventStreamResponse(ctx, eventCh), nil
}

No *gin.Context cast. No io.Pipe. No goroutine. No reference to c.Writer that can escape the request lifetime.

Why this fixes everything ​

The concurrent Flush race is gone. There is only one goroutine that ever touches the ResponseWriter: gin's handler goroutine, which is now blocked inside VisitGetWorkspaceEventsResponse running our select loop. Goroutine B no longer exists.

The use-after-free is gone. Our Visit method runs inside the handler goroutine. When the request ends — either because ctx.Done() fires or because a write fails — Visit returns, the dispatcher returns, and gin cleans up the ResponseWriter. Nothing else holds a pointer to it.

The misleading log is gone. Each write attempt has one code path — if it fails, we log and return. There is no unconditional "success" line outside the error check.

The discarded error is gone. Both heartbeat and event write errors are logged and cause the loop to exit cleanly.

The "Headers already written" warning is gone. When a write fails (client dropped before ctx.Done() fired), we return nil from Visit rather than the error. This prevents the ResponseErrorHandlerFunc from trying to write a 500 status on top of an already-started 200 response. The error is logged; gin cleans up normally. SSE disconnections are not application errors.

A note on the headers ​

The generated GetWorkspaceEvents200TexteventStreamResponse.VisitGetWorkspaceEventsResponse sets Content-Type: text/event-stream and writes the 200 status. But since we implement our own type that satisfies GetWorkspaceEventsResponseObject, the generated type's Visit is never called. The strict handler dispatches directly to our type. We own full responsibility for every header.

This is why the headers in VisitGetWorkspaceEventsResponse are not redundant — they are the only place those headers get set. We also add Cache-Control: no-cache and Connection: keep-alive, which the generated type doesn't include but which are SSE best practice: no-cache prevents any proxy from buffering the stream, and keep-alive signals the connection intent explicitly.

What the Event Hub Does ​

The WorkspaceEventHub in internal/note/infra/workspaceevent/workspaceevent.go is the source of events. It:

  1. Publishes workspace change events to a Redis Stream — a distributed queue that survives multiple service instances
  2. Runs a single internal router goroutine that reads from Redis and fans events out per workspace onto an in-memory gochannel
  3. When Subscribe(ctx, workspaceID, userID) is called, it subscribes to the per-workspace internal topic and returns a <-chan app.WorkspaceEvent

The goroutine inside Subscribe translates raw Watermill messages into typed app.WorkspaceEvent values, skips events from the same user (your own changes don't echo back to you), and drops events when the subscriber's channel buffer is full rather than blocking the fan-out.

The key contract between the hub and the SSE layer: the returned channel is closed when the context is cancelled. Our Visit loop handles this with case evt, ok := <-r.eventCh: if !ok { return nil } — a closed channel means the subscription is done and we exit cleanly.

Lessons ​

Codegen is a contract, not a cage. oapi-codegen generates GetWorkspaceEvents200TexteventStreamResponse as a convenience for simple streaming scenarios. The real extensibility point is the GetWorkspaceEventsResponseObject interface. Implementing that interface on your own type gives you complete control while staying within the framework's dispatch model.

If two goroutines touch the same http.ResponseWriter, you have a data race. http.ResponseWriter is not documented as safe for concurrent use. The sync.Mutex in the old code was protecting the wrong level of abstraction — it guarded the PipeWriter but left the ResponseWriter unprotected.

A goroutine that outlives its request is a ticking clock. The old Stream goroutine held c.Writer — a pointer into gin's request state. Once the request finished and gin began cleanup, that pointer became a landmine. The fix is to ensure the goroutine that drives the SSE loop is the request's goroutine, so its lifetime is naturally bounded by the request.

select does not guarantee order among ready channels. When ctx.Done() and ticker.C are both ready at the same instant, Go picks one at random. The old code relied on the select eventually picking ctx.Done(). It would — eventually. But "eventually" is not the same as "before the next heartbeat tick." This is why the goroutine could call Flush() on a cleaned-up ResponseWriter even after the context was cancelled.

Log lines that appear in pairs are a red flag. "failed to send heartbeat" followed immediately by "sent heartbeat" at the same timestamp is a goroutine saying contradictory things because the success log was placed outside the conditional. If your structured logger shows success and failure for the same operation in the same millisecond, there is a bug nearby.
